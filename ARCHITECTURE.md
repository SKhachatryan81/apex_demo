# Apex — Architecture & DevOps Guide

This document covers the infrastructure, deployment pipeline, and operational design behind Apex. It's written from a DevOps/platform perspective — for what the app itself does, see [README.md](./README.md).

---

## 1. High-level overview

```
                                   ┌─────────────────────────┐
                                   │        Docker Hub        │
                                   │  (image registry)         │
                                   └────────────▲─────────────┘
                                                │ push (CD)     │ pull (nodes)
                                                │                ▼
 GitHub Actions ──terraform apply──▶  GCP Project (gd-gcp-internship-devops)
      │                                          │
      │                              ┌───────────┴────────────┐
      │                              │   VPC (apex-network)     │
      │                              │   ├─ Cloud SQL (postgres, private IP)
      │                              │   └─ GKE cluster (apex-gke-cluster)
      │                              │        └─ apex-app-node-pool (preemptible)
      │                              │             ├─ ns: apex-app      → ingress-nginx, backend, frontend, migrate Job
      │                              │             └─ ns: apex-monitoring → Prometheus, Grafana, Loki, Alertmanager
      │                              └─────────────────────────┘
      └──helm upgrade──▶ Kubernetes objects (Deployments, Services, Ingress, Secrets, ConfigMaps, Jobs)
```

Single external entry point: one `ingress-nginx` controller (installed once, in `apex-app` namespace) fronts everything — the app itself, and Grafana under a sub-path. It's bound to one static external IP (`ingress_ip`).

## 2. Cloud infrastructure (Terraform)

All infra is provisioned by Terraform, state stored remotely in a GCS bucket (`apex-capstone-bucket`) — so local and CI runs share the exact same state, no drift between them.

### Module breakdown (`terraform/modules/`)

| Module | Responsibility |
|---|---|
| `network` | VPC, subnet, Cloud NAT (so nodes without external IPs still reach the internet — e.g. to pull images from Docker Hub), a static external IP for the ingress controller, and the private-services VPC peering range Cloud SQL needs |
| `cluster` | The GKE cluster itself plus one node pool: `apex-app-node-pool` (preemptible/Spot, autoscales 1–5, runs everything app- and monitoring-related). The cluster is VPC-native (`ip_allocation_policy {}`, GKE auto-creates the pod/service secondary ranges) — required so pods can reach Cloud SQL's private IP across the VPC peering |
| `sql` | Cloud SQL for PostgreSQL, private-IP-only (no public endpoint), password generated by Terraform (`random` provider). Has `deletion_protection` and daily backups with point-in-time recovery |
| `helm_app` | The `apex-app` namespace, the `db-creds` / `dockerhub-creds` / `app-secrets` Kubernetes Secrets, the `app-configmap`, and the `ingress-nginx` controller Helm release |
| `helm_monitoring` | Just creates the `apex-monitoring` namespace — the actual monitoring stack (Prometheus/Grafana/Loki) is installed by the CD pipeline via `helm upgrade`, not by Terraform, so it can be iterated on without a full `terraform apply` |

### Why a Docker registry isn't provisioned by Terraform

Earlier iterations of this project self-hosted a Nexus repository manager inside the cluster as the image registry. It was removed entirely in favor of **Docker Hub**. Self-hosting a registry inside the same cluster that pulls from it turned out to be a genuine architectural trap:

- Nexus needed its own registry address for CI pushes (external) vs. node pulls (internal) — easy to get wrong, and did get wrong (an internal `*.svc.cluster.local` DNS name doesn't resolve at the node/containerd level at all, only inside pods).
- Serving the registry over plain HTTP (no TLS) meant every node's containerd needed explicit insecure-registry trust configuration — implemented as a DaemonSet writing `/etc/containerd/certs.d/.../hosts.toml` and restarting containerd. A bug in that config (adding `config_path` to `config.toml` while a legacy `registry.mirrors` block was still present — containerd rejects that combination) caused containerd to crash-loop on **every node in the cluster**, cluster-wide, repeatedly, as GKE's auto-repair kept recycling nodes into the same broken state.

Docker Hub sidesteps this entire category of problem: it's plain HTTPS with a publicly trusted CA, so nodes trust it by default — no DaemonSet, no insecure-registry config, no internal/external address split.

## 3. Container images & registry

- Images: `docker.io/<dockerhub-user>/apex:backend-<git sha>` and `:frontend-<git sha>`, built and pushed by the `docker` job in CD.
- Pull secret: `dockerhub-creds`, a `kubernetes.io/dockerconfigjson` Secret created by Terraform (`helm_app` module), keyed under the fixed Docker Hub auth URL `https://index.docker.io/v1/` (required — a bare `docker.io` key won't match).
- Every commit gets its own tag. Before, the tags were static (`:backend`/`:frontend`), so `helm upgrade` saw no change and pods kept running the old image (a fixed frontend once sat on Docker Hub for 12+ minutes before anyone noticed). With a new tag every time, every deploy is a real rollout and `helm rollback` goes back to the exact previous image.

## 4. Kubernetes layout

### Namespaces

- `apex-app` — the application, ingress controller, and the DB migration Job
- `apex-monitoring` — Prometheus, Grafana, Loki, Alertmanager

### `apex-app` workloads

| Resource | Purpose |
|---|---|
| `apex-back-deployment` | Backend API, 2 replicas, ports `5001` (API) and `9091` (metrics). Readiness probe on `/health`, TCP liveness probe, CPU/memory requests |
| `apex-front-deployment` | Frontend (nginx serving the built Vite bundle), 2 replicas, readiness/liveness probes. (It used to wait for the backend with an `initContainer`; removed because nginx only serves static files and doesn't need the backend to start) |
| `apex-backend-svc` | ClusterIP, exposes both `http` (80→5001) and `monitoring` (9091) named ports |
| `apex-frontend-svc` | ClusterIP, 80→80 |
| `apex-app-ingress-ingress-nginx-controller` | The one ingress controller for the whole cluster, `LoadBalancer` type, bound to the static `ingress_ip` |
| `apex-ingress` | Path rules for the app (`/api` → backend, `/` → frontend), `ingressClassName: nginx`, request body capped at `1m` |
| `apex-migrate-job` | A Helm **pre-upgrade/pre-install hook** `Job` — runs `npm run migrate` (Umzug/Sequelize migrations) against Cloud SQL before every deploy rolls new app pods, using the same backend image tag being deployed. Up to 3 attempts (`backoffLimit: 2`). Self-deletes on success (`hook-delete-policy: hook-succeeded`) so it doesn't pile up; a failed Job is kept for `kubectl logs` and cleared by the next deploy (`before-hook-creation`) |
| `apex-backend-servicemonitoring` | `ServiceMonitor` that tells Prometheus Operator to scrape `apex-backend-svc`'s `monitoring` port at `/metrics` every 30s. Labeled `release: kube-prometheus-stack` — Prometheus only picks up ServiceMonitors carrying that label |

### Ingress routing (single controller, path-based)

One controller, two `Ingress` objects. An Ingress can only route to Services in its own namespace, so Grafana's rule lives in a separate `apex-monitoring` chart in the `apex-monitoring` namespace; the controller merges both into one nginx config on the same IP (longest prefix wins).

| Path | Routes to | Defined in |
|---|---|---|
| `/api` | `apex-backend-svc` | `apex-ingress` (`k8s/apex-app`, ns `apex-app`) |
| `/grafana` | `kube-prometheus-stack-grafana` | `apex-monitoring-monitoring-ingress` (`k8s/apex-monitoring`, ns `apex-monitoring`) |
| `/` (catch-all) | `apex-frontend-svc` | `apex-ingress` (`k8s/apex-app`, ns `apex-app`) |

Paths are passed through unrewritten — the backend receives `/api/...`, and Grafana is configured to serve from `/grafana` (see §6).

### Secrets & config flow

Terraform creates the Secrets/ConfigMaps; the app charts only *reference* them (never define credential values themselves):

```
GitHub Actions secrets ──TF_VAR_*──▶ Terraform variables ──▶ Kubernetes Secrets/ConfigMaps
                                                                 ├─ db-creds        (Cloud SQL creds)
                                                                 ├─ dockerhub-creds (image pull secret)
                                                                 ├─ app-secrets     (JWT secrets, salt)
                                                                 └─ app-configmap   (CORS_ORIGIN, JWT expiry)
```

`CORS_ORIGIN` is set to `http://<ingress_ip>` — it has to be a full origin (scheme + host), not a bare IP, or the backend's `cors` middleware silently rejects every real browser request (it does exact string matching against the `Origin` header).

`VITE_API_URL` is a **build-time** value (Vite bakes `import.meta.env.*` into the static JS bundle) — passed as a Docker `--build-arg` during the CI image build, pointed at `http://<ingress_ip>/api`. It can't be injected at runtime/deploy-time the way the backend's env vars can; get it wrong and the frontend silently falls back to `http://localhost:5001/api` — which, from a real user's browser, means "my own machine," not the cluster.

## 5. CI/CD pipeline (GitHub Actions)

### `ci.yaml`
Runs on every push: backend migrations + integration tests against a real `postgres:15` service container (not mocks), frontend build + tests, and an `infra` job that runs `terraform fmt`/`validate` and `helm lint`.

### `cd.yaml` — runs after CI succeeds on `main` (or manually)

```
terraform ──▶ docker ──▶ kubernetes
```

`workflow_run` fires whenever CI *completes*, pass or fail, so the first job is gated with `if: workflow_run.conclusion == 'success' || workflow_dispatch`; the later jobs `need` it and are skipped along with it.

1. **`terraform`** — `terraform init` (GCS backend), `terraform plan -out=tfplan`, then `terraform apply tfplan` (applies exactly the saved plan), then reads back `ingress_ip` as a job output for the other jobs. Variables come in as `TF_VAR_*` env vars from GitHub secrets.
2. **`docker`** — builds and pushes both images tagged with the commit SHA (needs `ingress_ip` for the frontend build-arg).
3. **`kubernetes`** — gets cluster credentials (`get-gke-credentials`), installs/updates the monitoring stack (`kube-prometheus-stack` + `loki-stack`, chart versions pinned), deploys the monitoring ingress chart, then deploys the app chart with `--wait --rollback-on-failure --timeout 10m` (the migration Job runs first as a pre-upgrade hook), overriding `global.repository` and both image tags via `--set`. Ends with a `curl --fail --retry 10` smoke test against `http://<ingress_ip>/`.

All jobs check out the commit that CI tested (`GIT_SHA` = `workflow_run.head_sha`, falling back to `github.sha` on manual runs — plain `github.sha` in a `workflow_run` is the tip of `main`, which may not have passed CI yet). Only one deploy can run at a time (`concurrency: group: cd`, `cancel-in-progress: false`); `destroy.yaml` shares the same group. A concurrency group holds one running + one pending run, so a newer pending run replaces an older pending one — fine for deploys (latest commit wins), but a queued destroy can be displaced by a deploy (and vice versa).

Tool versions are pinned: Terraform 1.17.0, Helm v4.3.1, ingress-nginx 4.15.1, kube-prometheus-stack 92.11.0, loki-stack 2.10.3.

### `destroy.yaml`
Manual only, gated behind typing the literal word "destroy" as a workflow input, and in the same `cd` concurrency group so it can't run mid-deploy. Only destroys the cluster (`module.cluster`, `module.helm_app`, `module.helm_monitoring`). The database has deletion protection, so it stays — together with the network it lives in — and the next CD run recreates the cluster with the data still there.

## 6. Observability stack

- **Metrics:** `kube-prometheus-stack` (Prometheus Operator + Prometheus + Alertmanager + Grafana + node-exporter + kube-state-metrics), installed via Helm directly in the CD pipeline (not Terraform-managed, so the monitoring config can be iterated without touching core infra).
- **App metrics:** the backend instruments itself with `prom-client` — request counts/latency histograms, DB query latency, default Node.js process metrics — served on a dedicated internal port (`9091`, separate from the API port) and picked up via a `ServiceMonitor` CRD (see §4). Prometheus Operator only scrapes targets declared through CRDs (`ServiceMonitor`/`PodMonitor`) — it does *not* honor the older `prometheus.io/scrape` pod-annotation convention, which is an easy trap if you're used to non-Operator Prometheus setups.
- **Logs:** Loki + Promtail (`loki-stack` chart, `promtail.enabled=true`), collecting cluster logs. `loki-stack` provisions its own Grafana datasource; CD sets `loki.isDefault=false` so it doesn't clash with the Prometheus datasource (see below).
- **Grafana behind a sub-path:** exposed at `/grafana` on the shared ingress rather than its own domain/IP. This requires telling Grafana about its own sub-path explicitly (`server.root_url` + `serve_from_sub_path: true` in `grafana.ini`) — without it, Grafana's internal redirects (e.g. after login) are root-relative and silently escape the `/grafana` prefix, landing the browser on whatever else the ingress routes `/` to.
- **Datasource conflicts:** both `kube-prometheus-stack` (Prometheus) and `loki-stack` (Loki) provision a Grafana datasource ConfigMap by default, and both default to `isDefault: true`. Grafana refuses to start if more than one datasource in an org is marked default — an easy thing to hit the first time you add a second data source to an existing Grafana install, and it fails as a hard crash-loop, not a soft warning.

## 7. Node pools & scheduling

| Pool | Machine type | Preemptible | Hosts |
|---|---|---|---|
| `apex-app-node-pool` | e2-standard-2 | Yes (Spot) | Everything — app, ingress, and monitoring |

There used to be a second, on-demand `apex-monitoring-node-pool`, but nothing was scheduled on it, so it was removed to stop paying for idle nodes.

**Trade-off, stated plainly:** the app pool is Spot to save cost, which means GCP can reclaim any node at any time. In practice this causes periodic, harmless-but-visible churn — pods briefly showing `NodeShutdown`, occasional transient `"No agent available"` errors from `kubectl`/Helm mid-operation while the Konnectivity proxy re-establishes after a node swap. It's not a bug; it's the cost trade-off of Spot capacity. A deploy that hits this mid-flight (e.g. a webhook call failing) just needs a retry.

## 8. Known limitations / honest gaps

Documented here on purpose, rather than glossed over — a capstone should show awareness of trade-offs, not just a happy path:

- **No HTTPS.** Everything is plain HTTP on the ingress IP. Needs a domain name first, then cert-manager + Let's Encrypt.
- **Monitoring runs on Spot nodes** without persistent storage, so Prometheus data and logs are lost when a node gets reclaimed.
- **Alertmanager doesn't send alerts anywhere** yet.
- **`loki-stack` is deprecated upstream.**
- **Single ingress-nginx replica on Spot nodes.** The controller runs the chart's default 1 replica, so a node reclaim takes all external traffic down until it's rescheduled.
- **Smoke test only covers the frontend.** It curls `/`, which nginx serves statically. The backend's `/health` is mounted outside `/api`, so the ingress sends it to the frontend; it also returns `200` even when the DB is unreachable (`"status": "degraded"`), so the backend readiness probe doesn't actually gate on the database either.
- **Backend liveness is a TCP check**, which passes even if Node's event loop is blocked.
- **Tests build the schema from models** (`sequelize.sync()`), while prod uses migrations. CI checks that migrations run, but not that they match the models.
- **Service Networking API isn't enabled by Terraform** (no `google_project_service`); it was turned on manually, so a fresh project would fail at the Cloud SQL peering step.
- **ingress-nginx is retired upstream** (no updates since March 2026). Works for now, should be replaced eventually.
- **CI uses a long-lived GCP credential** (`GCP_SA_KEY`). Workload Identity Federation would be better.
